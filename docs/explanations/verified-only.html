Verified Only — count only what the tape backs

Paper mode assumes fills. Verified Only recomputes every window from the fills the recorded trade prints corroborate. A window with zero confirmed fills drops out entirely. Read it as a tape-backed subset, not a bound or an estimate: removing an unverified losing fill can raise the shown net, and the weak level check can include fills the queue check would reject.

1 · The one-line rule

Same window, confirmed numbers only — or null (dropped) when verified.trades === 0. Copies trades, cost, payout, net, up/down fills, fees from window.verified. Pending windows keep net = null.

Everything downstream — KPI cards, PnL curve, bars, window log — reads the same effective slice, so they can never disagree. The API summary only backs the all-time, every-fill view.

4 · Verified vs Attainable — the full difference

Two different questions on the same tape. Verified = weak level check. Attainable = strict queue check. A fill can be verified but phantom.

Rule of thumb: verified over-counts, attainable under-counts queue-unknown fills. BUY prints never fill a resting bid — getting that backwards inverts the audit. Taker fills always pass attainable (they take the ask); they never pass verified in paper mode.

Per-fill live verdicts in Orders & Fills → STATUS: Attainable as soon as selling so far could fill it, Phantom once complete tape proves it could not. Verified stays only until the audit judges it.

5 · Operational gotchas

  • Old runs look empty: live verifier only stamps the window it is trading. Runs started before it existed keep fills unstamped → re-stamp with python bot/verify_run.py (see bot/RUNBOOK.md), else the view covers a slice.
  • Fees change meaning: taker fees excluded, maker only badge appears; maker rebate still applies (drawn from maker pool).
  • Corroboration line under chart: confirmed maker vs all maker, never-traded count, unchecked taker count, payout resting on unverified fills.
